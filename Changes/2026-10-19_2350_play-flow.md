# ArchipelagoVic 2.5.2: the Play flow (Game profiles, step 4)

**Date:** 2026-10-19 23:50 (local time)
**Request:** "Go on to step 4 (the Play flow: patch, start EmuHawk and the client, open the room)." This is step 4 of Game profiles with a one-click Play button. Play has to:
1. ask for the room address or an archipelago.gg room link;
2. patch the ROM next to the patch file, skipping that when it's already done;
3. start EmuHawk with `--lua=<connector_bizhawk_generic.lua> "<patched rom>"`;
4. start `ArchipelagoBizHawkClient.exe --connect <server>` without the patch file;
5. open the room in a Play tab with `joinRoom`.

Each step shows its progress, and any failure gets a plain-language error and leaves nothing half-started.

This is the main-process and renderer logic. The profile screen and the progress list come in step 5, so the version stays 2.5.2 until then.

## How Play runs

`playGame(profileId, { patch, server, password }, onProgress)` in `renderer/launcher.js` reports every step to `onProgress` as `{ step, state, text }`, with state `running`, `done` or `failed`.

| Step | Done by | What happens |
|---|---|---|
| `server` | window, then main | A room link is turned into its current address with the existing `roomAddress` (it wakes a sleeping room and reads its port through `web:json`). Then the main process checks that something answers at that address. |
| `check` | main | The step 3 `checkProfile` with this session's patch: EmuHawk, the ROM's MD5 and the patch. It also checks that the connector script and `ArchipelagoBizHawkClient.exe` are in the install. |
| `patch` | main | The step 1 helper with `--rom`. It's skipped ("Already patched: …") when the patched game is still there and was made from this same patch and ROM. A stamp in `config.patched` records each file's size, time and the ROM's MD5. |
| `emuhawk` | main | Starts `EmuHawk.exe --lua=<Archipelago>\data\lua\connector_bizhawk_generic.lua <patched game>`, then waits 2.5 s to make sure it didn't close straight away. |
| `client` | main | Starts `ArchipelagoBizHawkClient.exe --connect <address>` (plus `--password` if given), checked the same way. **The patch file is not passed:** in `worlds/_bizhawk/context.py:353-355` the server stored in a patch replaces `--connect`, and that port goes stale when a room restarts. |
| `room` | window | `joinRoom({ server, slot, room, connect: true })` opens the room in a Play tab as the patch's slot, so the activity feed shows too. |

- **Nothing starts on failure:** if anything fails, the step says why, and everything this run had started is closed (`killTree`).
- **One at a time:** only one Play can run at once.
- **After a successful Play,** the profile remembers this patch, and the server as typed (the link or the address), in `lastServer`. The screen will pre-fill it next time.

## Files

- **`main.js`:**
  - new: `serverAnswers`, `startAndWatch`, `patchHelperProblem`, `fileStamp` and `playProfile`;
  - IPC `play:start`, which sends `play:progress` events to the window that asked.
- **`preload.js`:**
  - `play`;
  - `onPlayProgress`, which returns a function that stops listening.
- **`renderer/launcher.js`:** `playGame`.

## Tested

**How the tests ran:**
- **Test copy of the app:** started with its own `--user-data-dir` and four test profiles. It was driven over the DevTools protocol by calling `playGame` in its window.
- **Test game:** a Pokémon Red game generated this session and hosted by the app's own Host code (`startServer`, port 38299).
- **Stand-in EmuHawk:** BizHawk isn't installed yet, so `EmuHawk.exe` was a tiny program compiled for the test. It only writes down the command line it was started with, then waits, or closes straight away when told to.

**17 of 17 passed** on the final run. The first two runs didn't get as far as Play, for reasons in the test setup:
- the test `config.json` was written with a byte-order mark, so the app read it as empty;
