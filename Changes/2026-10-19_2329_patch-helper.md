# ArchipelagoVic 2.5.2: patch helper (Game profiles, step 1)

**Date:** 2026-10-19 23:29 (local time)
**Request:** "Plan approved. Start step 1 (the patch helper)." This is step 1 of Game profiles with a one-click Play button. Play has to patch the ROM using the frozen Archipelago install, with no Archipelago window or file picker. Try the Launcher/BizHawk Client route first, then a hidden helper, and keep whichever works reliably.

This step adds the helper only. Nothing in the window uses it yet, so the version stays 2.5.2. The version bump and the README update come with the Play button.

## Which way of patching, and why

Both options were tried for real on Archipelago 0.6.8 with a generated Pokémon Red patch (see Tested).

**A. `ArchipelagoBizHawkClient.exe "<patch>"` with `rom_start: false`: not used.**
- It patched correctly. But the **"Archipelago BizHawk Client 0.6.8" window opened** about 5 seconds later and stayed open until it was closed by hand.
- The reasons are in the 0.6.8 source, `worlds/_bizhawk/context.py`:
  - after patching, `launch()` always opens the client window;
  - it connects to the server stored in the patch file, which replaces `--connect` (lines 353-355). That is the stale-port problem Play is meant to avoid;
  - a failed patch shows a pop-up message box and gives ArchipelagoVic nothing it can read.
- It also needs `rom_start` changed in `host.yaml` and restored afterwards.

**B. A hidden helper, "ArchipelagoVic Patch": used.**
- **How it runs:** ArchipelagoVic starts it the same way as the Logic helper:
  `ArchipelagoLauncherDebug.exe "ArchipelagoVic Patch" -- [--inspect] [--rom BASE_ROM] PATCH_FILE`
- **What it does:**
  1. Sets `settings.no_gui`, so a missing base ROM is an error, never a file picker (`settings.py:93`).
  2. Sets `settings.skip_autosave`, so Archipelago never rewrites `host.yaml` when the helper exits (`settings.py:839`).
  3. Finds the game's patch class.
  4. Checks the base ROM's MD5.
  5. Calls `Patch.create_rom_file`, which writes the patched game next to the patch file the way Archipelago does.
  6. Reports the result as one `APVIC {json}` line.
- **Results:** no window, about 2.6 s, and output byte-identical to option A's.
- **No temporary `host.yaml` changes at all.** `--rom` sets the base ROM for that run only. ArchipelagoVic will still save the profile's ROM to `host.yaml` (step 2), so Archipelago's own tools use it too.

## What the helper reports

**`--inspect`** reports what the patch needs, without patching:
- the game;
- the patch and result file endings;
- the expected base-ROM hash (the patch class's `hash`);
- where the patched game will go;
- the server and player name stored in the patch;
- which `host.yaml` setting holds the base ROM, for example `pokemon_rb_options.red_rom_file`. It finds this for any game by matching the expected hash against each ROM setting's accepted hashes.

**Patching** returns `{"type": "patched", "written": …}`, or `{"type": "error", "code": …}`. The error codes are:
- `patch-missing`;
- `no-handler` (no installed game makes this kind of patch);
- `no-rom-setting`;
- `rom-missing`;
- `hash-mismatch` (includes the ROM's actual hash);
- `crash`.

ArchipelagoVic will turn these into plain-language messages in step 3. One example: when the hash is Blue's and the patch is for Red, it will say "this is Pokémon Blue, but this patch is for Red".

## Other findings
- **Every patch carries its own expected hash.** Its `archipelago.json` has `base_checksum` (`worlds/Files.py:310`). For example, the test patch had `"base_checksum": "3d45c1ee9abd5738df46d2bdda8b57dc"`. ArchipelagoVic can read it straight from the patch.
- **Where the stored server comes from.** Patches generated on this PC store an empty `server`. Patches downloaded from an archipelago.gg room store that room's address, and that is where the stale port comes from.

## Tested

All tests ran on this PC with Archipelago 0.6.8 (frozen). The test game was a single-player Pokémon Red game, generated with `ArchipelagoGenerate.exe` from a temp Players folder: seed `14228189917825565134`, slot `VicTest`.

- **Option A:** run from a temp folder holding its own `host.yaml` copy (`red_rom_file` set, `rom_start: false`), so the real `host.yaml` was never touched.
  - It patched in about 1 s; the patched ROM's MD5 was `90bbb5c6f02a4f395a68a0f716f82bcd`.
  - The client window opened at about 5 s and stayed open. I closed it with `taskkill`.
- **Option B, inspect:** no window. It reported game "Pokemon Red and Blue", expected hash `3d45c1ee…57dc` and the setting `pokemon_rb_options.red_rom_file`.
- **Option B, patch with `--rom ROM\Pokemon Red.gb`:** no window, 2.6 s. Output MD5 `90bbb5c6…`, identical to option A.
- **Option B, error cases.** Each had no window and wrote no file:
  - a copy of Red with one byte changed (made in the temp folder, never in `ROM\`) gave `hash-mismatch`, actual hash `5e088b3b…bc70`;
  - the Blue ROM for a Red patch gave `hash-mismatch`, actual hash `50927e84…bd8b`;
  - no `--rom`, with `host.yaml` pointing to a ROM that doesn't exist (your current setting), gave `rom-missing`. No file picker opened;
  - a `.apxyz` file gave `no-handler`;
  - a patch path that doesn't exist gave `patch-missing`.
- **`host.yaml`:** its SHA-256 was the same before and after every run (`1F34E6C9…32FF`).
- **`main.js`:** passes `node --check`.
- **Clean-up:**
  - every client process I started was closed;
  - the temp folder, with the test game, patches, patched ROMs and the one-byte-changed copy, was deleted.
- **The add-on in `custom_worlds`:** the new `apvic_logic.apworld` was installed there to test it, the same file `ensureBridge` would write. It now has both helpers.
